# 11. COSMA/DiRAC batch harness — fanning the evaluations out (sub-project 3)

## What this is for

The project's evaluations — the external-LLM benchmark, the orchestrator multi-part eval, and the
understanding-agent eval — are **embarrassingly parallel**: each job (a question, or a question × model
pair) is independent, needs no communication with any other, and is dominated by a single LLM call. That
is the textbook fit for an HPC array job. `src/batch_harness.py` shards a list of jobs, runs each shard
as one SLURM array task on COSMA/DiRAC, and aggregates the per-shard outputs into one results table.

The harness **only schedules and collects** — every number still comes from the existing deterministic
evaluators (`benchmark_external`, `orchestrator_eval`, `understanding_eval`). It computes nothing itself,
so the trust invariant is untouched.

## Flow

```
build_jobs(kinds, models)          # enumerate corpora -> stable unique job ids
   -> shard(jobs, N)               # deterministic round-robin: balanced, disjoint, complete
   -> run_shard(shard_id, runner)  # one SLURM array task; per-job error captured, JSONL out
   -> aggregate(shard_*.jsonl)     # merge, sort by id, dedup (re-run safe) -> results.csv
```

The committed `hpc/jena_eval.slurm` (generated by `python -m src.batch_harness plan …`) is the array
script: `#SBATCH --array=0-(N-1)`, each task running `run-shard --shard $SLURM_ARRAY_TASK_ID`. Nothing
site-specific is baked in — `--account`, `--partition`, `--time`, and `--out-dir` are inputs.

## Key correctness property: sharding is result-preserving

The claim that makes the fan-out trustworthy is that **the aggregated result does not depend on how many
shards you use**. Proven on the real 19-job corpus (benchmark + orchestrator + understanding) with a
deterministic runner:

```
shards=1: rows=19  summary={'n': 19, 'ok': 19, 'correct': 9}
shards=2: rows=19  summary={'n': 19, 'ok': 19, 'correct': 9}
shards=4: rows=19  summary={'n': 19, 'ok': 19, 'correct': 9}
shards=8: rows=19  summary={'n': 19, 'ok': 19, 'correct': 9}
result-preserving (1 vs 8 shards): True
```

This is enforced in the suite by `test_run_local_is_result_preserving_across_shard_counts` and the
partition properties in `test_shard_is_a_balanced_partition` (union == all jobs, disjoint, sizes differ
by ≤ 1). Re-running a shard is safe because `aggregate` de-duplicates by job id (last write wins).

## Real end-to-end local run (30 July 2026, `local` mode, `llama3.2:3b`)

Running the *actual* evaluators through the harness (no SLURM — `local` mode runs every shard
in-process, the dev/offline path):

```
real local run: 19 rows in 52.0s   (num_shards=4)
overall: {'n': 19, 'ok': 19, 'correct': 15}
  benchmark    : {'n': 8, 'ok': 8, 'correct': 8}
  orchestrator : {'n': 3, 'ok': 3, 'correct': 2}
  understanding: {'n': 8, 'ok': 8, 'correct': 5}
```

- **benchmark 8/8** — the app matches the dataset ground truth on every case (the truth layer == pandas;
  during the run the faithfulness gate visibly rejected four invented LLM numbers and fell back to the
  exact template, which is the gate working as designed).
- **orchestrator 2/3** — consistent with doc 10, but note it scored **3/3 in an earlier run**: the 3B
  decomposer is **non-deterministic**, so multi-part coverage varies run-to-run. Fanning the same job
  out many times on the cluster is exactly how you'd quantify that variance cheaply.
- **understanding 5/8** — matches doc 09's LLM-on figure.

This is the first time all three evaluations run through **one** driver and land in **one** results
table — which is the practical payoff of the harness even before any cluster is involved.

## Honest limits

- **The cluster run itself was not executed here.** The Python core and the generated `sbatch` script are
  verified (11 offline tests; a real local run); actually submitting to DiRAC is the reproducible next
  step, gated only on an allocation and Ollama/API availability on the compute nodes.
- **Speed-up is real but bounded by LLM throughput, not CPU.** Wall-clock is dominated by model latency
  and (on a shared cluster) queue time. Array parallelism gives near-linear speed-up in the *number of
  concurrent model endpoints*, so the win is large for a big (question × model) sweep and negligible for
  a handful of jobs. Each array task still needs its own Ollama instance or an API key.
- **It schedules, it doesn't judge.** No metric lives here; correctness is entirely the existing
  evaluators'. That is deliberate — the harness must not become a second, divergent source of numbers.

## Reproduce

```bash
cd code/v1
# generate the array script (writes hpc/jena_eval.slurm + hpc/jobs.jsonl):
python3.12 -m src.batch_harness plan --kinds benchmark,orchestrator,understanding \
  --models llama3.2:3b --num-shards 4 --out-dir hpc \
  --account dpXXX --partition cosma --time 02:00:00

# run the whole thing locally (no SLURM) and aggregate:
python3.12 -m src.batch_harness local --kinds benchmark,orchestrator,understanding \
  --num-shards 4 --out hpc/results_local.csv

# on COSMA instead:
sbatch hpc/jena_eval.slurm
python3.12 -m src.batch_harness aggregate --glob 'hpc/shard_*.jsonl' --out hpc/results.csv
```
